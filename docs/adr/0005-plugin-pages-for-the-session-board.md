# The Session Board is a plugin; core gains sandboxed plugin pages

Status: proposed. Decides #4433. Terms follow `CONTEXT.md`: **Board**, **Column**, **Card**, **Stage**, **Signal**, **Rule**; a **Plugin** contributes **UI slots**.

Issue #3446 settled on a plugin-first Board, and the read-only `kanban-lite` prototype (#3456) stalled because plugins had no page surface, no way to write per-session state from the browser, and a worker cannot read other plugins' slot values. We considered a native core Board and rejected it: the Board serves a subset of users and would add product surface to core that maintainers do not want to own. Instead core grows one general capability, a `page` UI slot: a plugin ships a single self-contained HTML file, the Web dashboard renders it in a sandboxed iframe, and a versioned `postMessage` bridge exposes a capability-gated API: the session list, the aggregated UI state of every installed plugin exactly as `GET /api/plugins/ui-state` already returns it to any authenticated client (no new cross-plugin state API, not the event log), the plugin's own actions, open-session navigation, archive and trash of any listed Session under `session.write`, and theme variables. `session.write` already authorises writes to any Session of the profile (`session.meta.set` takes an explicit session id); the "attached session" wording in the plugin API docs is stale and #4463 corrects it. The Board (`agent-of-empires.kanban`) is the first consumer.

## Loading and confinement

- The frame is `sandbox="allow-scripts"` and nothing else: no `allow-same-origin`, so the document has an opaque origin with no access to the dashboard's storage, cookies or token; no `allow-forms`, `allow-popups` or `allow-top-navigation`, so it cannot submit, open windows or navigate the dashboard.
- The bundle is not loaded through `srcdoc`: a `srcdoc` document inherits the dashboard policy, whose `script-src 'self'` would refuse the bundle's inline script, and a policy inside the frame cannot lift an inherited one. Instead the Daemon serves the bundle at a dedicated authenticated route and the iframe's `src` points there, so the response carries its own policy. The frame request is initiated by the dashboard and is same-site, so cookie authentication applies; how the route authenticates when device binding is on is settled in #4460.
- That route's policy is `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; connect-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors 'self'`, with the frame-denying headers relaxed to same-origin on this route only. `'unsafe-inline'` is deliberate: the bundle is the only content of an opaque-origin document that can load nothing else, so a nonce or hash would add serve-time work without narrowing anything. The policy blocks every subresource load, fetch and connection, including the GitHub image hosts and `ws:`/`wss:` the dashboard policy permits.
- The bridge host identifies the page by `event.source` against the iframe it created (the opaque origin serialises as `null`, so `event.origin` is useless), then validates the envelope version and schema, resolves plugin identity from that frame, checks the declared capability, and only then acts. Messages failing any step are dropped.
- Sandbox and policy cover subresources, fetches, connections, forms, popups and navigation of other contexts. They do not cover the frame navigating itself: `navigate-to` was withdrawn from CSP, and the embedder's `frame-src` is enforced on child-initiated navigation by Chromium but not Firefox, so a page could leave with bridge data in a URL. This residual channel is accepted and bounded by the trust model: pages exist only for installed plugins, the bridge exposes the user's own Session metadata, featured plugins are reviewed, and the dashboard tears the frame down when the bridge handshake is lost. The bridge stays the only sanctioned data path and its surface stays minimal.

## Consequences

- Plugin JavaScript never runs on the dashboard origin and never sees the access token; everything it can do is enumerated by the bridge and gated by manifest capabilities.
- Writes from a page are fire-and-forget through the existing plugin `action` endpoint; results surface through the UI-state poll. A request/response channel is deferred until a plugin needs it.
- Per-session plugin state lives in `session.meta`; plugin-wide state in `plugin.storage`. Core gains no Board-specific schema or migration.
- Confirms direction A of #3446 with the extension points it anticipated.
